A1 — endpoint.rs (EndpointConfig + serde)
Ошибки и пробелы
Нет валидации port. port: 0 проходит как валидный u16, но это невалидный порт. Значения > 65535 отсекаются serde как MalformedJson (косвенно), но 0 — нет. 
Нужна явная проверка port != 0.
Нет валидации host и sni. Пустые строки ("") принимаются. Как минимум host должен быть непустым; желательна базовая проверка формата хоста/DNS-имени и что sni не 
пустой (иначе TLS-клиент в A3 получит пустой SNI).
Нет #[serde(deny_unknown_fields)]. Лишние/опечатанные поля в JSON молча игнорируются — это скрывает ошибки конфигурации с Dart-стороны. Для fail-closed-подхода из 
AMO_SPEC стоит запретить неизвестные поля.
Нет проверки дубликатов эндпоинтов. Два одинаковых host:port пройдут — деградирует смысл failover-приоритетов.
Регистр hex не нормализуется. is_ascii_hexdigit() принимает и A-F, и a-f. Само по себе ок (в A3 from_str_radix тоже принимает оба), но поведение нигде не зафиксировано 
тестом — потенциальный источник рассинхрона.
Нет trim/пробелов. Пробелы в hex → WrongHexLength, а не понятная ошибка. Мелочь, но сообщение об ошибке будет путать.
server_pub/psk валидируются, но не декодируются здесь. Реальное hex-декодирование живёт в A3 (decode_hex32). Значит валидная по длине/символам строка всё равно может 
дать проблему при декодировании нечётной длины — но 64 фикс. длина это закрывает. Ок, но логика раскидана по двум местам (дублирование hex_decode/decode_hex32).
Необходимые тесты (в дополнение к 9 имеющимся)
port == 0 → ошибка (после добавления валидации).
port > 65535 → MalformedJson.
пустой host / пустой sni → ошибка.
hex в верхнем регистре ("AA".repeat(32)) → принимается (зафиксировать контракт).
неизвестное лишнее поле в JSON → поведение (ошибка при deny_unknown_fields).
дублирующиеся эндпоинты → ошибка (если решите запрещать).
граница длины hex: 63 и 65 символов → WrongHexLength с правильными expected/got.
JSON-объект вместо массива ({...}) → MalformedJson.

A2 — failover.rs (первая версия, строки ~203–460)
Критично: две конфликтующие версии failover.rs
В черновике A2 представлен дважды и версии несовместимы:
Версия 1 (этот диапазон): new() -> Result<Self, &'static str>, поле marked_bad_at, states: Mutex<Vec<EndpointState>>, есть can_switch(), 
нет last_switch/failure_count/last_switch_unix_ms/is_in_cooldown.
Финальная версия (ниже по документу): new() -> Self (без Result), поле last_failure, states: Vec<Mutex<EndpointState>>, есть failure_count, last_switch_unix_ms, 
is_in_cooldown, нет can_switch.
A3/A4 и интеграционные тесты написаны под финальную версию (Arc::new(FailoverManager::new(endpoints)) без unwrap, вызов is_in_cooldown(host, port)). С версией 1 
проект не скомпилируется. Нужно оставить одну версию и удалить вторую из плана.
Ошибки и пробелы (по версии 1)
Счётчик consecutive_failures не сбрасывается при переключении. После switch у покинутого эндпоинта остаётся = 3. Когда cooldown пройдёт и вернёмся к нему, первый же 
report_failure() даст ≥ FAILURE_THRESHOLD → мгновенный повторный уход, не дав эндпоинту нормального шанса. Сброс происходит только в report_success(). Нужно сбрасывать 
счётчик старого (или нового) эндпоинта в try_switch().
TOCTOU / гонка на current_idx. В report_failure guard current_idx берётся и отпускается в temporary (let idx = *self.current_idx.lock()...;), затем states лочится 
отдельно, затем ещё раз. Между чтением idx и try_switch() (который снова лочит current_idx) другой поток может изменить индекс → двойной инкремент/двойное переключение. 
SOCKS5-прокси спавнит по задаче на соединение — многопоточность реальна.
current_idx и states — раздельные мьютексы. Возможны несогласованные снимки состояния. Лучше единый мьютекс на всё состояние (idx + states) либо атомарный дизайн.
report_failure возвращает bool, но при «все в cooldown» продолжает наращивать счётчик и на каждой последующей неудаче снова зовёт try_switch() вхолостую. Не баг, но 
лишняя работа/лог-шум.
Cooldown завязан на Instant::now() напрямую — нетестируемо. 60-секундный per-endpoint cooldown невозможно проверить в юнит-тестах без ожидания реального времени. Нужна 
абстракция часов (инъекция now/трейт Clock), иначе критерий приёмки AMO №4 («Cooldown 60s») остаётся непокрытым.
FAILOVER_MIN_INTERVAL/FAILURE_THRESHOLD не проверяются на согласованность с AMO_SPEC в тестах (60s, «переключение по timeout, не по error» — последнее обеспечивается в 
    A3, но контракт «report_failure не вызывается на protocol error» здесь никак не выражен).
Нет метода отчёта для статуса (failure_count, last_switch_*), который требует A4/transport_get_status и правка Ревизора №4. В версии 1 их нет → FFI-статус не соберётся.
Необходимые тесты
переключение ровно на пороге FAILURE_THRESHOLD (есть) + что до порога не переключается (есть).
сброс счётчика при переключении (после исправления бага) — вернуться к эндпоинту после cooldown и убедиться, что он не «выкидывается» с первой неудачи.
per-endpoint cooldown истёк → эндпоинт снова доступен (требует инъекции часов).
все эндпоинты в cooldown → try_switch() = false, индекс не меняется (частично есть через can_switch).
конкурентный стресс-тест: N потоков зовут report_failure/report_success параллельно → отсутствие паник, консистентный индекс.
report_success сбрасывает marked_bad_at и снимает cooldown (сейчас теста на снятие cooldown нет).
порядок обхода кандидатов по кругу (idx+step)%len начиная с текущего+1 (детерминированный приоритет из AMO_SPEC).
report_failure НЕ вызывается на protocol-error (контрактный тест — логичнее в A3, но зафиксировать связку).
Главная рекомендация
Сначала устранить дублирование A2 (оставить одну каноническую failover.rs), затем ввести инъекцию часов ради тестируемости cooldown и починить сброс счётчика при switch.
Без этого критерии приёмки AMO №3, №4 и №9 формально не закрываются.

Сверил черновик A3 с реальными исходниками из ветки wip-flutter (proxy.rs, tls.rs). API TlsClient::new(Vec<String>) -> Result, connect(host,port) (делает 
    resolve+TCP+TLS), steal::client_handshake(&mut stream, &server_pub, &psk) и FrameCodec::new(...) — совпадают с тем, что использует черновик. Ниже разбор A3 
    (строки 468–967).
A3 — интеграция FailoverManager в proxy.rs
Критично
Steal-handshake попал внутрь connect_fut → нарушение антифингерпринт-правила AMO. В финальной версии connect_current_endpoint внутрь future засунуто всё: TlsClient::
connect + crate::steal::client_handshake + FrameCodec::new. А ветка Ok(Err(e)) => { failover.report_failure(); ... } дергает report_failure() на любую ошибку этого 
future — включая ошибку steal-handshake. Но AMO_SPEC прямо требует: failover только по timeout/refused/DNS/TLS-handshake-fail и НЕ по protocol error mid-handshake 
(иначе DPI-fingerprint по частой смене IP). Это регресс: в первой версии A3 steal-handshake стоял после connect_with_failover, вне зоны report_failure — правильно. В 
финале контракт сломан. client_handshake нужно вынести из connect_fut обратно в handle_connection, после установления соединения.
GATEWAY_CONNECT_TIMEOUT (10с) оборачивает и steal-handshake тоже. Как следствие того же: медленный/битый custom-протокольный хендшейк засчитается как "gateway connect 
timeout" → report_failure(). То есть protocol-phase-задержка триггерит failover — снова фингерпринт. Таймаут должен покрывать только connect+TLS, не steal.
Тесты, которые ничего не проверяют (ложная уверенность)
switches_to_secondary_on_connection_refused не тестирует proxy.rs. Он поднимает good_listener, bad_port, но потом никак их не использует — просто зовёт failover.report_
failure() 3 раза напрямую. Это дубликат юнит-теста FailoverManager, а не интеграционный тест. Реальный путь (поднять Socks5Proxy, подключиться SOCKS5-клиентом, увидеть 
    переключение) не покрыт вообще. good_listener/unused_port — мёртвый мишурный код.
does_not_switch_on_protocol_error_mid_handshake — no-op. Он не прогоняет никакой protocol error через прокси: просто sleep(10ms) и assert что индекс не сменился. Он 
подтверждает пустоту. Хуже — он маскирует баг №1 выше: реальный код сменил бы endpoint на ошибке steal-handshake, а тест это не ловит, потому что ничего не вызывает.
min_cooldown_60s_enforced_per_endpoint — сам автор уже отметил правку is_in_cooldown("127.0.0.1", 1111). Это верно (сигнатура из финала A2 — (host: &str, port: u16)). 
Остаётся замечание: тест проверяет только «сразу в cooldown», но не истечение 60s (без инъекции часов — как и отмечено в A2).
Логика/семантика
Нет retry внутри одного соединения + порог 3. Финальная версия сознательно fail-fast: одна попытка current_endpoint(), при неудаче report_failure() и REP_FAILURE 
клиенту. Но switch происходит только после FAILURE_THRESHOLD = 3. Значит при падении шлюза три отдельных браузерных соединения должны сломаться (три неудачных загрузки 
    страниц), прежде чем произойдёт переключение — и только четвёртое соединение попадёт на новый endpoint. Это стоит явно зафиксировать против критериев приёмки AMO: 
    «переключение при отказе» не бесшовное, а с задержкой в 3 фейла. Если критерий требует переключения в пределах одного пользовательского действия — текущая модель 
    ему не удовлетворяет.
report_success() не вызывается, если connect прошёл, но ack != "OK". Сеть исправна (TCP+TLS+steal ок), а счётчик неудач текущего endpoint не сбрасывается. Здоровый 
шлюз, вернувший не-OK, останется со «стухшим» consecutive_failures от прошлых попыток. Мелочь, но нелогично.
Глобальный key: [u8;32] стал мёртвым. Поле хранится как _key и нигде не используется — шифрование теперь идёт на session_key из steal-handshake, а server_pub/psk 
берутся из endpoint. При этом Dart-слой (A5/A6) продолжает передавать sharedSecret → key_bytes в transport_start. Итог: sharedSecret в настройках ни на что не влияет. 
Либо задействовать ключ, либо убрать его из FFI-контракта и UI, иначе это тихая дезинформация конфигурации.
Мелкие / пробелы
Тройное дублирование hex-декодирования. decode_hex32 (A3) ⟂ validate_hex_field/подразумеваемый декодер (A1). Раньше был ещё hex_to_32/hex_decode (промежуточная версия 
    A3, потом убрана). Нужна одна общая утилита (crate::util или endpoint.rs), декодирующая и валидирующая hex64→[u8;32], чтобы A1 и A3 не расходились.
TlsClient::new(...) строится на каждое соединение. Внутри — RootCertStore + webpki_roots::TLS_SERVER_ROOTS заново при каждом handle_connection. Это уже было в оригинале, 
но теперь per-endpoint; стоит вынести общий ClientConfig/connector в Socks5Proxy один раз, а SNI задавать per-connect.
Всё в cooldown → тихий REP_FAILURE. Когда все endpoints в cooldown, остаёмся на текущем, connect падает, report_failure без switch, клиент получает REP_FAILURE. 
Fail-closed корректен, но нет никакого сигнала наверх (в статус/лог) о состоянии «все в cooldown» — диагностика для transport_get_status была бы полезна.
Комментарий про // ── 4. пропал / нумерация шагов сбита относительно оригинала — косметика, но затрудняет ревью diff.
Список необходимых тестов для A3
Настоящий интеграционный тест через SOCKS5: поднять Socks5Proxy::run() на эфемерном порту, подключиться tokio-SOCKS5-клиентом, primary = refused/timeout, secondary = 
живой mock-gateway (с корректным steal-handshake mock либо через фейковый steal), и проверить, что после порога соединения идут на secondary. Текущий тест этого не делает.
Тест, что ошибка steal-handshake НЕ вызывает report_failure (после выноса handshake из connect_fut): mock-gateway, у которого TCP+TLS ок, но custom-handshake рвётся → 
current_index не меняется, failure_count активного endpoint не растёт. Сейчас это утверждение декларируется, но не проверяется — и код его нарушает.
Тест разделения таймаута: connect+TLS уложился в лимит, но steal-handshake висит → не должно квалифицироваться как connect-timeout-failover.
Тест connect-timeout → report_failure: primary = «чёрная дыра» (принимает TCP, не завершает TLS в 10с) → срабатывает GATEWAY_CONNECT_TIMEOUT, report_failure вызван.
Тест DNS-fail / refused → report_failure отдельно (несуществующий хост; закрытый порт).
Тест ack != "OK": соединение успешно, gateway вернул не-OK → клиент получает REP_FAILURE, report_failure НЕ вызван, и (после исправления) report_success вызван, счётчик 
сброшен.
Тест «все endpoints в cooldown»: connect_current_endpoint возвращает Err, клиент получает REP_FAILURE, индекс не меняется.
Тест SOCKS5-парсинга: IPv4/DOMAIN/IPv6 ATYP, отказ не-CONNECT команды, отказ при отсутствии NO_AUTH — эти ветки в handle_connection не покрыты ни одним тестом.
Тест per-endpoint SNI: после переключения TlsClient создаётся с vec![endpoint.sni] именно нового endpoint (регрессия из промежуточного патча, где SNI брался из 
    глобального пула).
Тест decode_hex32: валидный hex64 → Some([u8;32]); длина ≠ 64 → None; не-hex символ → None.
Резюме A3
Главная проблема — регресс антифингерпринта: steal-handshake и его таймаут оказались под report_failure(), что прямо противоречит AMO_SPEC, а два из трёх 
«интеграционных» тестов этого не ловят (они фактически пустые). Второй по важности пункт — мёртвый глобальный key при живом sharedSecret в UI (тихая дезинформация 
конфигурации) и семантика «3 фейла до переключения» без внутрисоединённого retry. Рекомендую: вынести handshake из connect_fut, сузить таймаут до connect+TLS, 
переписать интеграционные тесты на реальный SOCKS5-путь, объединить hex-декодирование и решить судьбу глобального ключа.

A4 — lib.rs (FFI: transport_start + transport_get_status + прочее)
Критично
transport_start возвращает 0 (успех) ДО того, как прокси реально забиндился. Функция спавнит std::thread, публикует слот и сразу return 0. Реальный proxy.run() 
(и TcpListener::bind внутри) выполняется асинхронно; если бинд упадёт (порт занят, нет прав), ошибка уйдёт только в eprintln!, а Dart уже получит 0 → state = running. 
Это прямое нарушение задекларированного fail-closed: «при малейшей неопределённости не стартуем». Нужен канал подтверждения (например oneshot/SyncSender), по которому 
поток сообщает результат бинда, и transport_start возвращает 0 только после успешного bind.
Паника через FFI-границу = UB. failover_slot().lock().unwrap() в transport_start и в transport_get_status паникует на отравленном мьютексе. extern "C" функции без catch_
unwind при развёртывании стека через FFI — неопределённое поведение. Обернуть тело каждой extern "C"-функции в std::panic::catch_unwind и возвращать -1/null при панике 
(особенно важно, т.к. это заявленный fail-closed-контракт).
Ручная сборка JSON в transport_get_status без экранирования. format!(r#"...{}"#, ep.host, ...) вставляет host сырым. host в A1 не валидируется на символы, так что хост 
с " или \ даст невалидный JSON → jsonDecode в Dart бросит исключение → getStatus() вернёт null. Использовать serde_json (serde_json::json!{...}.to_string()) вместо 
строковой интерполяции.
Ошибки жизненного цикла (stop/restart)
transport_stop — no-op, возвращающий 0. Он не останавливает поток и не освобождает SOCKS-порт (это честно помечено TODO B1), но возвращает успех, и Dart-слой ставит 
state = idle. Последствие: связка stop→start сломана — второй start() попытается забиндить тот же порт, bind упадёт, но (см. баг №1) transport_start всё равно вернёт 
0 и покажет running, а трафик пойдёт через старый поток. Как минимум transport_stop должен возвращать не-0 или явно документировать в Dart, что рестарт невозможен без 
перезапуска процесса.
Слот ACTIVE_FAILOVER не сбрасывается в transport_stop. Поэтому transport_get_status() после «остановки» вечно отдаёт {"running":true,...}, противореча Dart-состоянию 
idle. Рассинхрон статуса.
Повторный transport_start течёт потоками и рантаймами. Каждый вызов спавнит новый std::thread + новый tokio::Runtime, старый не завершается. Нет защиты «уже запущен» 
на Rust-стороне (она есть только в Dart через _state, но FFI можно дёрнуть напрямую).
Мёртвый ключ (сквозная проблема A3↔A4↔A5)
key: [u8;32] копируется из key_bytes и передаётся в Socks5Proxy::new(bind, failover, key), но в A3 он лёг в _key и не используется. Значит key_bytes из FFI (и 
sharedSecret из Dart-UI, A5/A7) ни на что не влияют — шифрование идёт на server_pub/psk из endpoint + session-key steal-handshake. Либо задействовать ключ, либо убрать 
его из замороженной FFI-подписи (но подпись объявлена frozen G-Contract — тогда хотя бы явно задокументировать, что параметр зарезервирован/игнорируется, чтобы UI не 
вводил пользователя в заблуждение).
Зависимости от A2, требующие сверки
transport_get_status вызывает fo.current_endpoint(), fo.failure_count(), fo.last_switch_unix_ms(). В финальной версии A2 failure_count/last_switch_unix_ms есть, а в 
первой — нет. Ещё одно подтверждение, что дублирующуюся первую версию A2 надо удалить, иначе lib.rs не соберётся. current_endpoint() должен возвращать владелец/клон 
(EndpointConfig), т.к. ep.host/ep.port читаются после снятия внутреннего лока — сверить, что там не возвращается ссылка на данные под мьютексом.
Socks5Proxy::new(bind, failover, key) и .with_rate_limit(bps) — сигнатуры предполагаются; сверить с A3 (там new изменил список параметров).
Мелочи / пробелы
std::ptr::copy_nonoverlapping(key_bytes, …, 32) читает ровно 32 байта; безопасно только пока Dart аллоцирует 32 (isConfigured требует sharedSecret.length==64). 
Приемлемо, но зависит от инварианта на другом конце FFI — стоит отметить в # Safety.
transport_version отдаёт указатель на static, а transport_get_status — heap через CString::into_raw. Разные контракты владения под одной «строковой» семантикой: если 
кто-то по ошибке вызовет transport_free_string на результат transport_version — UB. В Dart сейчас корректно (version не освобождается), но это ловушка; задокументировать.
socks_port == 0 приведёт к биндингу на эфемерный порт — не ошибка, но не то, что ожидает UI; можно отклонять 0.
Rust-side default rate-limit отсутствует (0 = no limit), а Dart при null подставляет 3 МБ/с — расхождение поведения «по умолчанию» между слоями (не баг, но зафиксировать).
Проблемы контрактных тестов ffi_contract.rs
valid_json_returns_zero почти ничего не проверяет. Из-за бага №1 transport_start вернёт 0 даже если прокси не забиндился, поэтому assert_eq!(ret, 0) пройдёт всегда. 
Тест не подтверждает, что транспорт реально поднялся.
Утечка потоков между тестами + гонка на глобальном слоте. Тесты по умолчанию идут параллельно, каждый спавнит вечный proxy-поток (нет transport_stop), и все мутируют 
общий ACTIVE_FAILOVER. Нужен #[serial] (crate serial_test) либо изоляция, иначе флаки и залипшие порты.
Хардкод портов (19999/19998/…). Возможны коллизии в CI. Лучше :0 (эфемерный) — но это упирается в отсутствие возврата фактического порта.
null_pointers_return_minus_one проверяет только endpoints_json == null. Нет кейса key_bytes == null (хотя код его обрабатывает).
Не покрыты transport_get_status, transport_free_string, transport_version, transport_stop вообще.
Необходимые тесты для A4
transport_start возвращает -1, когда порт уже занят / bind невозможен (после исправления бага №1 с подтверждением бинда).
transport_start c key_bytes == null → -1.
transport_start c endpoints_json, содержащим >16 элементов / пустой массив / битый JSON → -1 (частично есть).
transport_get_status до старта → строго {"running":false}.
transport_get_status после успешного старта → валидный JSON, парсится, содержит running:true, current_endpoint.host/port, failures, last_switch_unix_ms.
transport_get_status при host, содержащем "/\ → валидный экранированный JSON (тест на баг с ручной сборкой).
transport_free_string(null) — no-op без паники; двойной вызов не тестировать (UB by contract), но проверить один корректный round-trip get_status→free без утечки 
(например под Miri/ASAN в CI).
transport_version → "0.2.0", не требует free.
transport_stop → зафиксировать текущий контракт (возврат 0) ИЛИ, после реализации, что порт освобождается и get_status даёт running:false.
Тест «паника не пересекает FFI»: смоделировать отравленный мьютекс/панику → функция возвращает -1/null (после добавления catch_unwind).
Тест повторного transport_start (идемпотентность/защита от двойного запуска) — сейчас поведение неопределённое.
Все FFI-тесты пометить #[serial].
Резюме A4
Основные проблемы — семантические, а не синтаксические: (1) transport_start рапортует успех до реального бинда, ломая fail-closed; (2) паника через FFI без 
catch_unwind — UB; (3) ручная сборка JSON без экранирования; (4) transport_stop/слот — no-op, из-за чего рестарт и статус рассинхронизированы; (5) сквозной 
мёртвый key. Контрактные тесты создают ложную уверенность (проходят из-за бага №1) и текут потоками на глобальном состоянии. Рекомендую: ввести подтверждение бинда 
через канал, обернуть все extern "C" в catch_unwind, перейти на serde_json для статуса, решить судьбу transport_stop+слота и глобального ключа, переписать тесты с 
serial_test и реальной проверкой поднятия/остановки.

A5 — endpoint.dart + transport_service.dart
GatewayEndpoint (модель)
isValid не проверяет, что serverPub/psk — реально hex. Проверяется только length == 64. Строка из 64 не-hex символов ("zzzz…") пройдёт isValid, дойдёт до 
transport_start, и упадёт уже на Rust-стороне decode_hex32 → None → отказ старта. Валидацию RegExp(r'^[0-9a-fA-F]{64}$') надо делать здесь, чтобы UI ловил ошибку до 
FFI. То же и для host (нет проверки на пробелы/мусор — коррелирует с багом экранирования JSON в A4 transport_get_status).
port не ограничен сверху. port > 0 пропускает port > 65535, а FFI-тип Uint16 в socks_port и Rust u16 в endpoint обрежут/переполнят. Нужно port >= 1 && port <= 65535.
fromJson небезопасен к типам. json['port'] as int бросит, если порт пришёл как double/String (частый случай при ручном редактировании JSON или миграции). Аналогично as 
String для отсутствующих ключей → null cast error, роняющий весь load(). Нужны безопасные касты с дефолтами/валидацией.
Нет ==/hashCode. Для reorder/dedup/тестов сравнение по значению отсутствует. Плюс это мешает выявлять дубликаты endpoint (замечание из A1 про duplicate endpoints — на 
    Dart-стороне тоже не решено).
transport_service.dart
_hexToBytes(_settings.sharedSecret) упадёт при нечётной/короткой строке. isConfigured гарантирует length == 64, но start() полагается на этот инвариант неявно; если 
кто-то вызовет start() в обход (или sharedSecret содержит не-hex), int.parse(..., radix:16) бросит, и хотя есть try/catch, keyPtr/endpointsPtr в этот момент ещё не в 
try/finally → возможна утечка при частичном пути. Сейчас _hexToBytes вызывается до try, а endpointsPtr уже аллоцирован до него → при исключении в _hexToBytes 
endpointsPtr не освобождается. Утечка нативной памяти.
_hexToBytes не проверяет длину результата = 32. Если sharedSecret = 64 hex → 32 байта, ок. Но цикл записи keyPtr[i] жёстко идёт до 32; при более коротком keyBytes будет 
RangeError. Инвариант держится только на isConfigured.
Мёртвый ключ (сквозная). keyPtr → transport_start(key_bytes) → Rust _key (A3/A4) не используется. sharedSecret из UI шифрование не задаёт. Это надо либо задействовать, 
либо явно пометить в UI как зарезервированное поле (см. A6/A7 ниже — там оно всё ещё обязательное).
getStatus() создаёт DynamicLibrary и делает lookupFunction при каждом вызове. Если UI поллит статус (типичный кейс для failover-индикатора), это дорого и потенциально 
утечка хендлов на некоторых платформах. Библиотеку/функции стоит кэшировать в поле сервиса.
stop() оптимистично ставит idle до вызова FFI, затем снова выставляет по результату. Но transport_stop в A4 — no-op, возвращающий 0 (порт не освобождается). Итог: UI 
показывает idle, а нативный поток жив и порт занят → следующий start() не сможет забиндиться (а transport_start из-за бага A4 всё равно вернёт 0). Рассинхрон, 
унаследованный из A4.
loadVersion() возвращает 'unknown' при ошибке, но _version при этом не меняется (остаётся '') — мелкое несоответствие между return value и полем.
toNativeUtf8() для endpointsJsonStr не освобождается на пути раннего исключения (см. первый пункт). На «нормальном» пути finally есть — ок.
Необходимые тесты A5
GatewayEndpoint.isValid: валидный; port=0/70000; пустой host; serverPub/psk длины ≠ 64; 64 не-hex символа (должен стать invalid после фикса).
fromJson/toJson round-trip; fromJson с port как double/String; с отсутствующими ключами → не роняет, а даёт ошибку/дефолт.
_hexToBytes: 64 hex → 32 байта; нечётная длина → контролируемая ошибка, не краш всего сервиса; не-hex → обработано.
start() при isConfigured == false → state=idle, сообщение выставлено, FFI не вызывается.
start(): отсутствие утечки нативной памяти при исключении в _hexToBytes (проверка, что оба указателя освобождены).
getStatus(): ptr.address == 0 → null; невалидный JSON → null без краша; корректный JSON → Map.
==/hashCode (после добавления).

A6 — settings_service.dart (мультиконечная + миграция)
Миграция вызывает save() до удаления legacy-ключей, но save() не трогает legacy — ок; однако нет транзакционности. Если процесс убьют между save() и prefs.remove(...), при следующем load() _keyEndpoints уже есть → ветка миграции не выполнится, legacy-ключи останутся навсегда (безвредно, но мусор). Приемлемо, стоит отметить.
load() не обрабатывает битый _keyEndpoints JSON. jsonDecode бросит и load() упадёт целиком → приложение не стартует. Нужен try/catch с фолбэком на пустой список (fail-safe, не fail-crash).
Дефолтный clientPsk/sniList — «зашитый тестовый PSK». Legacy-геттер clientPsk при пустом списке возвращает константу ABCDEF…. Автор пишет, что теперь это «безопаснее», но геттер всё ещё раздаёт тестовый PSK любому коду, который его дёрнет. Лучше вернуть '' и пусть isValid/isConfigured отсекут.
isConfigured требует sharedSecret.length == 64, но sharedSecret — мёртвый ключ (A3/A4). Пользователь обязан ввести 64-символьный секрет, который ни на что не влияет. Это UX-ловушка прямо в критерии готовности: без «ключа-пустышки» транспорт не стартует. Согласовать с решением по мёртвому ключу.
Нет валидации socksPort (диапазон/занятость) и нет проверки на дубликаты endpoint при addEndpoint.
endpoints — публичное изменяемое поле (не через методы). settings_screen пишет в него напрямую (s.endpoints = _endpoints) в обход save()-обёрток addEndpoint/removeEndpointAt/reorderEndpoint, из-за чего эти методы фактически не используются UI (см. A7). Дублирование API.
load() не проверяет валидность мигрированного endpoint. Legacy server_public мог быть пустым → создаётся невалидный endpoint, который потом молча не пройдёт isConfigured. Диагностики нет.
Необходимые тесты A6
Миграция: legacy-ключи заданы → endpoints[0] собран корректно, legacy-ключи удалены, новый ключ записан.
Миграция при пустом legacyHost → endpoints == [], ничего не пишется.
Идемпотентность: второй load() после миграции читает multi-формат, не запускает миграцию повторно.
load() с битым _keyEndpoints JSON → пустой список, без исключения (после фикса).
save()/load() round-trip списка из N endpoints.
addEndpoint/removeEndpointAt/reorderEndpoint меняют список и персистят.
isConfigured: пустой список → false; валидный список + 64-hex secret → true; невалидный endpoint в списке → false; secret ≠ 64 → false.
Legacy-геттеры при пустом списке возвращают безопасные значения (после фикса — не тестовый PSK).

A7 — settings_screen.dart
Dismissible + ReorderableListView конфликтуют по key и по индексам. key: ValueKey('${e.host}:${e.port}:$index') включает index — при reorder индексы меняются, ключи 
«переезжают», что ломает и анимацию reorder, и корректность dismiss (Flutter требует стабильные ключи для обоих виджетов). Ключ должен быть стабильным идентификатором 
endpoint, не зависящим от позиции (нужен id/== в модели — см. A5). При двух endpoint с одинаковыми host:port ключи ещё и не уникальны без index → runtime-ошибка 
дубликата ключей.
onDismissed вызывает _removeEndpointAt(index) с захваченным index из itemBuilder. После reorder/удаления соседей этот индекс может указывать не на тот элемент → 
удаление не того endpoint. Классический баг «stale index в замыкании».
_save() пишет s.endpoints = _endpoints напрямую, минуя addEndpoint/removeEndpointAt из A6 — то есть весь продуманный API сервиса не задействован, а save() вызывается 
вручную. Дублирование и риск рассинхрона.
_save() не валидирует sharedSecret и endpoints перед start(). Если secret не 64 hex или список пуст, start() внутри выставит idle+сообщение, но экран уже сделает 
Navigator.pop(context) — пользователь не увидит ошибку, вернётся назад с неработающим транспортом. Нужно проверять isConfigured до pop и показывать ошибку.
_save(): await start(); ... Navigator.pop — между await и pop нет проверки mounted для Navigator (есть только перед start). После длинного start() контекст мог 
инвалидироваться.
_socksPortCtrl парсится с фолбэком 18080 без валидации диапазона (0–65535). Ввод 99999 молча станет 18080 — тихая потеря ввода.
Диалог _EndpointEditDialog использует context после await-подобного показа SnackBar внутри _submit — сам по себе ок, но isValid там опять только по длине hex (не 
    проверяет hex-символы), см. A5.
maxLength: 64 на secret/pub/psk показывает счётчик символов (обнажает длину секрета) и не мешает вставить не-hex. Косметика + валидация.
Нет поля/индикатора для мёртвого/живого sharedSecret-статуса — пользователь не понимает, зачем секрет, если шифрование по факту на endpoint psk (сквозная неоднозначность).
Редактирование существующего endpoint отсутствует — только add/remove/reorder. Чтобы исправить опечатку в host, нужно удалить и создать заново. Функциональный пробел 
против «управление списком endpoint».
Необходимые тесты A7 (widget-тесты)
Пустой список → отображается «No endpoints configured», reorder-список не строится.
Добавление через диалог: невалидный endpoint → SnackBar, диалог не закрывается; валидный → добавлен в список.
Reorder: перетаскивание меняет порядок; ключи стабильны (тест на отсутствие duplicate-key/ stale-index после фикса модели).
Dismiss (swipe): удаляется именно свайпнутый endpoint, а не сосед (регресс-тест на stale index).
Дубликат host:port: список из двух одинаковых endpoint не роняет UI (после стабильных ключей).
_save() при невалидной конфигурации → нет Navigator.pop, показана ошибка; при валидной → start() вызван и pop.
socksPort вне диапазона → отклонён/скорректирован с уведомлением (после фикса).
Проверка mounted после await start() (тест на dispose экрана во время сохранения).
Сквозные выводы по A5–A7
Мёртвый sharedSecret/key проходит через все три слоя (модель нейтральна, сервис требует 64 hex, UI требует ввод) — но в Rust (A3/A4) он не используется. Это главная 
сквозная неоднозначность: либо задействовать, либо убрать/пометить зарезервированным во всех трёх местах разом.
Валидация hex только по длине повторяется в A5 (isValid), A6 (косвенно) и A7 (диалог) — нужна одна общая функция isHex64() и её применение везде; иначе не-hex доходит 
до FFI и падает поздно.
Стабильные идентификаторы endpoint (id/==) отсутствуют в модели, из-за чего reorder+dismiss в A7 содержат реальные баги (stale index, duplicate keys).
API сервиса (A6) не используется UI (A7) — addEndpoint/remove/reorder дублируются ручными манипуляциями списком в экране; стоит выбрать один путь.
fail-crash вместо fail-safe в load() (битый JSON роняет старт приложения) — противоречит духу fail-closed из спеки (закрываться безопасно, а не падать).
